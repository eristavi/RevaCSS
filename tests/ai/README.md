# AI guidance evaluation

This directory records five complete interfaces generated by Codex in the
documentation-improvement conversation on 16 October 2026. The prompts,
documentation revision and generation method are in `scenarios.json`; original
HTML outputs are in `fixtures/`. They are one documentation-conditioned output
batch, not an independent or blind model comparison.

## Run the focused evaluation

From the repository root, with Python 3.10+ and matching compiled `dist/` files:

```sh
npm run test:ai-guidance
python3 tests/ai/evaluate.py --json
```

No model request, package installation, browser run or network operation is
performed. The command rechecks the committed output batch; it does not generate
fresh AI responses. Obtain/build matching CSS through the normal workflow if
the fixture stylesheets are absent.

The evaluator checks explicit scenario requirements and selected structural
contracts: supported attribute values, shared root settings, source stylesheet
paths, scoped boundaries, material dependencies/order, required native structure,
unique IDs, label/error/popover associations and documented form markup.
Fourteen deliberately broken variants must fail with the expected diagnostic.
These controls help demonstrate that the evaluator rejects concrete mistakes.

It is a focused fixture evaluator, not a general-purpose RevaCSS linter. Its
class/attribute policies apply to these prompts; application-defined classes,
attributes and custom palettes can be declared in scenario metadata. Its simple
HTML parser and file-name checks do not replace browser parsing, computed CSS,
native activation, hydration or accessibility review.

The form fixture is a server-returned error-state template, including an
explicit application-supplied CSRF placeholder and known `/projects` endpoint.
It is not a complete working form endpoint by itself. The separate
`examples/ai-application/` demonstrates actual request validation and storage.
Likewise, fixture navigation destinations require the host application's routes.

## Evaluate another output batch

1. Choose representative prompts and objective acceptance requirements before
   generating outputs; preserve the requested framework/version and supplied
   documentation context.
2. Record model/provider identity when available, date, documentation revision,
   original prompt and unedited response. Do not overwrite a failing original
   with a corrected response and count it as first-pass success.
3. Add scenarios/fixtures and validate relevant contracts. Preserve negative
   controls and extend them for new failure modes. Record unsupported checks
   rather than interpreting their absence as a pass.
4. Review actual browser behaviour and application/framework boundaries where
   authorized and applicable; a static pass cannot establish them.
5. Record results in a new dated quality record, with file hashes and evidence
   limits. Separate first-pass generation, repairs and documentation changes.
6. If a failure exposes an unclear instruction, update the source guide and
   reference, then generate a fresh batch for comparison. Keep the earlier
   evidence instead of rewriting its history.

Provider/model comparisons and fresh generations need their own runs and
recorded context. The initial batch supplies a repeatable static baseline; it
does not justify a universal AI reliability percentage or a 10/10 certification.
